# データモデル

fortee の参加者管理は、カンファレンス → イベント → チケット種別 → 参加者（チケット 1 枚 = 1 行）という階層で構成される。URL は [urls.md](urls.md) を参照。

## イベント

チケットを販売・配布する単位である。本番では「カンファレンス本編」「前夜祭」「懇親会」「託児所」の 4 つが登録されている。

| 属性 | 内容 |
| --- | --- |
| ID | UUID（URL で使用）。フォームの select では内部の数値 ID も使われる |
| スラッグ | 例: `yapc-tokyo-2026`, `yapc-tokyo-2026-eve-party`, `yapc-tokyo-2026-reception`, `yapc-tokyo-2026-nursery` |
| チケット販売中 | 一般ユーザにチケットショップを表示するか（スタッフにはオフでも表示される） |
| フォーム項目編集可能 | 参加者が発券後にフォームを編集できるか |
| API有効 | 参加者一覧 API を有効にするか（[data-sources.md](data-sources.md)） |
| ウェルカムメール | 発券時に送るメールテンプレート |
| ウォレット拡張設定 | Apple/Google ウォレット用の iBeacon UUID と追加表示項目（2 つまで） |

本番のイベント ID は、本編 `8b2e79c9-9301-4dca-ac12-7b686a1ec85e`、前夜祭 `87e485da-0d45-432b-9943-4a5a3728bb2b`、懇親会 `78db606a-1e93-41b9-a531-7791dd68eee0`、託児所 `64478c06-1fb2-4286-a7ab-32d0b2c9f350` である。

## チケット種別

イベントに属し、チケット番号の採番単位になる。管理画面では「設定 → イベント → チケット販売/無料配布」で編集する。

| 属性 | 内容 |
| --- | --- |
| ID | UUID |
| 名前・価格 | 価格 0 で無料配布。有料販売は Stripe 連携（クローズドβ）が必要 |
| プレフィックス | チケット番号の接頭辞。`A` なら `A-1`, `A-2`, … と連番採番。発券後にプレフィックスを変えても採番済みの番号は変わらない |
| 最大販売数・購入可能数 | 在庫と 1 ユーザあたりの上限（0 で無制限） |
| 販売期間 | 開始・終了日時 |
| スポンサーチケット | アクセスコードの対象にする |
| 非表示チケット | 一覧に出さずアクセスコード入力で表示 |
| 前提条件 | 指定したチケットのいずれかを所有するユーザだけが購入できる（詳細は次項） |

### チケット種別の前提条件（チケット間の依存関係）

チケット種別には「前提条件」として、同じカンファレンスの他のチケット種別（他イベントのものを含む）を複数指定できる。指定したチケットのいずれかを所有するユーザだけがそのチケットを購入でき、条件は OR である。設定は次の場所で確認できる。

| 場所 | 内容 |
| --- | --- |
| イベント詳細画面のチケット種別一覧 | 「前提チケット」としてプレフィックスの一覧（例 `A`）が表示される |
| チケット種別の編集フォーム | 「前提条件」欄にカンファレンス内の全チケット種別がチェックボックスで並び、チェック済みが前提。input 名は `ticket_types[_uuids][{チケット種別UUID}]` |

ダウンロード CSV、一覧の HTML 断片、参加者一覧 API のどれにも前提条件は出ない。独自システムで依存関係を使うなら、設定画面から読み取って設定として持つ。なお、ここで使うチケット種別 UUID は、チェックイン画面のフィルタ `at` に使う参加者タイプ UUID とは別の値である。

本番の設定は次のとおり（2026-11-07 に設定画面を閲覧）。前夜祭と託児所はスタッフチケット以外の本編チケットのいずれか、懇親会は本編の対応する種別を前提にしている。

| イベント | チケット種別 | 前提条件（いずれか） |
| --- | --- | --- |
| 本編 | A, B, C, D, P, Q, S, X, Z | なし |
| 前夜祭 | M | X, A, B, C, D, S, P, Q |
| 懇親会 | I 一般 | X, A, C, D |
| 懇親会 | J 学生 | B |
| 懇親会 | K スポンサー | S |
| 懇親会 | L ゲスト・スピーカー | P, Q |
| 託児所 | E, F, G, H | X, A, B, C, D, S, P, Q |

前提条件は購入時の制約であり、fortee は購入後の整合を保証しない。Sandbox で前夜祭チケットに「A 所持」の前提を付けた後、A をすべてキャンセルした状態のスタッフアカウントで前夜祭チケットを購入できた（キャンセル済でも所有扱いになるのか、スタッフには制約が効かないのかは切り分けられていない）。また本編チケットをキャンセルしても、先に購入した前夜祭チケットはキャンセルされない。YAPC::Tokyo 2026 では、前夜祭チケットの所有者が本編チケットをキャンセルしたときは前夜祭チケットも合わせてキャンセルする運用で整合を保っている。本番では 2026-11-07 時点で、有効な前夜祭チケット 141 枚の所有者全員が有効な本編チケットも持っていた（一覧の「他チケット」から集計。キャンセル済の前夜祭チケットは 5 枚）。

## 参加者タイプ

「設定 → 参加者タイプ」で管理する。チケット種別（チケットタイプ）とイベントに紐づけ、タグの自動付与などに使う。チェックイン画面の「チケット種別」フィルタ（`at`）の値は、この参加者タイプの UUID である（本番画面の select から確認）。

## 参加者（チケット）

参加者は「チケット 1 枚につき 1 行」である。同じユーザが本編と前夜祭のチケットを持てば参加者は 2 行になり、それぞれの詳細画面に「これ以外の参加者」として相互に表示される。本番でも、スピーカーが一般チケットをキャンセルしてスピーカーチケットに移った例や、1 人で同じイベントのチケットを複数枚持つ例がある。

| 属性 | 内容 |
| --- | --- |
| 参加者ID | UUID。管理画面の詳細 URL に使う |
| チケットID | UUID。購入完了 URL にも現れる |
| チケット番号 | `プレフィックス-連番`（例 `M-1`） |
| ユーザ | fortee アカウント（表示はハンドル名）。同一人物の判定はこれで行われている。ユーザ名が fortee 全体で一意か、退会や変更の後に別人が同じユーザ名を取れるか（再利用）は未確認（[README](README.md) の未確認事項） |
| 参加者タイプ（チケット種別名） | 例「テスト前夜祭チケット」 |
| キャンセル済 | 参加者一覧に「キャンセル済」の表示付きで残る |
| チェックイン | 日時（分単位表示）または「未チェックイン」 |
| チケットトークン | 32 文字の英数字。参加者向け URL `/{conf}/attendee/{チケットトークン}` に使う。この URL は未ログインでも 200 を返す（本番で確認、ヘッダのみ） |
| profile_url_token | 32 文字の英数字。URL `/{conf}/attendee/{profile_url_token}/go-profile` に使う |
| フォーム回答 | イベントのフォーム項目（設定 → イベント → フォーム項目。タイプは見出し・説明文・空白・テキスト 1 行/複数行・ラジオ・チェックボックス・セレクト・住所・電話番号・メールアドレス・Twitter・名前・表示名）への回答。項目ごとに必須、「参加者一覧に表示する」、「API出力時のキー」、対象チケット種別を設定する。回答は詳細画面、ダウンロード CSV（項目名の列）、一覧表示にした項目は一覧にも出る |
| 名前、Twitter アカウント | 参加者（チケット）ごとの属性で、ダウンロード CSV の `Name`・`Twitter` 列に出る。何が埋めるかは未確認（下記） |
| タグ、シリアルコード、スポンサー、フラグ（無効・レビュー完了・アバター要レビュー） | 詳細画面で編集（画面確認のみ） |

### 名前と Twitter アカウント

参加者の「名前」「Twitter アカウント」は、fortee ユーザのプロフィールの値ではなく、参加者（チケット）ごとの属性である。2026-11-09 に次のことを確かめた。

- karupanerura のユーザ設定（`/users/edit`）では「お名前」と「Twitter」がどちらも設定済みだが、同じユーザの Sandbox の参加者（A-1、A-2、M-1、M-2）の詳細はすべて「名前（未設定）」「Twitter アカウント（未設定）」で、ダウンロード CSV の `Name`・`Twitter` 列も空だった
- A-2 は「名前」タイプのフォーム項目（お名前）に回答しているが、参加者詳細の「名前」は未設定のままだった。参加者自身のチケット詳細とチケット一覧、オーガナイザのバルク追加とシリアルインポートにも、名前と Twitter アカウントを入れる欄はなかった
- 本番の本編イベントの参加者一覧の全 750 行（キャンセル済を含む）の詳細を閲覧し、名前と Twitter アカウントが設定された参加者は 0 件だった（本番の閲覧で確認。前夜祭と懇親会は見ていない）

何がこの属性を埋めるか（スピーカーや招待者の登録など、見ていない経路）は未確認である。

### 2 種類のトークン

参加者は 2 種類のトークンを持ち、どちらも参加者（チケット）ごとに別の値である。

| トークン | 使われる場所 | 取得経路 |
| --- | --- | --- |
| チケットトークン | チェックイン用 QR（`fortee:` 付き）、チェックイン API の `code`、チケット詳細 URL、ウォレットのバーコード、フィードバック QR | 管理画面一覧のチケットリンク、ダウンロード CSV の Ticket url 列、参加者詳細 |
| profile_url_token | 一括チェックイン CSV、プロフィール QR（go-profile URL）、QR コード PDF の印字 | 参加者詳細のプロフィール QR リンク、ダウンロード ZIP の `qr-profile/` 画像のデコード、QR コード PDF の文字列 |

両者に互換性はなく、チケットトークンを一括チェックイン CSV に書いても「Attendee not found」になる。

profile_url_token がユーザごとではなくチケットごとの値であることは、Sandbox の ZIP で確かめた。同じユーザ（karupanerura）が持ち、ZIP を作った時点（2026-11-07。A-1 と A-2 はその後にキャンセルした）で有効だったチケット 3 枚（テスト本編の A-1 と A-2、テスト前夜祭の M-1）の `qr-profile/` の画像をデコードすると、3 枚とも別の値で、どのチケットトークンとも一致しなかった。同じイベントの 2 枚（A-1 と A-2）でも値が違うので、ユーザごとの値ではない。未発券の A-3 も、User name が空のまま profile_url_token を持っていた。

### 発券済と未発券

未発券の参加者は、管理画面の「バルク追加」（参加者タイプと「数字部分の最大値」または `+n` を指定してチケット番号を先に採番する）で作られ、後からチケットが発券されるとチケット番号順に引き当てられる。スポンサーチケットやスピーカーチケットを名札作成のために先に採番しておく用途で、チェックイン画面の「未発券の参加者を含めて集計する」はこれを指す。

未発券の参加者は、ユーザもメールも空のまま、参加者 ID・チケット番号・チケットトークン・profile_url_token を既に持ち、チェックイン API でも発券済みと同じように扱われる（Sandbox で A-2 を作成し、状態取得で `unused`、状態更新で `used` になることを確認）。一覧ではチケット番号の隣に「未発行」と表示され、表示には「未発券の参加者も表示」（クエリ `u=1`）が要る。

発券が引き当てられても、参加者 ID・チケットトークン・profile_url_token・チェックイン状態はそのまま維持される（Sandbox で未発券の A-2 を API でチェックイン済みにした後、同じチケット種別を発券したところ A-2 に引き当てられ、両トークンと 17:05 のチェックイン日時が残った）。引き当てで埋まるのはユーザ、メール、発券日時、フォーム回答である。

### キャンセル済

キャンセルすると参加者は一覧に「キャンセル済」付きで残り、チケット番号は再利用されない。チェックイン API は「キャンセル済のチケットです」で拒否し、ダウンロード ZIP には含まれない。一覧の HTML 断片には含まれる。
