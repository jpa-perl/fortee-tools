# fortee の仕様調査

fortee（https://fortee.jp）の参加者チェックイン機能を調べた結果である。受付アプリ（[PRD](../../prd.md)）は fortee と直接通信せず、ダウンロード ZIP の取り込みと一括チェックイン CSV の反映で fortee に依存する。その取り込みと反映に関わる仕様を、ここにまとめる。

| [data-model.md](data-model.md) | イベント・チケット種別・参加者の構造、識別子とトークン、発券状態 |
| [qr-code.md](qr-code.md) | チェックイン用 QR の内容と表示場所、ウォレット・PDF の QR |

| [constraints.md](constraints.md) | 独自のチェックイン機構を作るときに、fortee 側の仕様から生じる制約 |

## 記述の確度

Sandbox（`yapc-tokyo-2026-sandbox`）で実際に操作して確かめた事実を「検証済み」、本番（`yapc-tokyo-2026`）の設定画面や一覧をそのまま読み取った事実を「本番の閲覧で確認」、画面の表示や公開 JS から推論した事実を「推定」と書き分けている。確度の記載がない記述は検証済みか、本番の閲覧で確認したものである。本番カンファレンスでは閲覧以外の操作を行っていない。

調査日は 2026-11-07 で、fortee の仕様はこの時点のものである。本番の閲覧による確認は 2026-11-09 と 2026-11-10 にも行い、該当箇所に日付を添えている。管理画面の API は公開仕様ではないので、利用前に Sandbox で再確認する。

## 未確認事項

| 未確認の事項 | 設計での扱い |
| --- | --- |
| `allowCheckIn` が `false` になる条件 | fortee 側の `allowCheckIn` に依存せず、スナップショットの状態で判定する |
| スタッフでないログインユーザがチェックイン API を呼んだときの応答 | チェックイン API は使わない（NFR-7） |
| 一括チェックイン CSV の行数上限 | CSV を指定した行数で分割して出力できるようにする（FR-45） |
| 一覧の HTML 断片（bare-list）を取得するときに必要なリクエストヘッダ | HTML 断片は使わない |
| チケット種別の前提条件が、キャンセル済チケットの所有者やスタッフにも適用されるか（Sandbox ではキャンセル済の A しか持たないスタッフが M を購入できた） | 前提条件に依存せず、受付の設定（FR-2）で所持が必須のイベントを判定する |
| ダウンロード CSV の `Name`・`Twitter` 列が何から埋まるか。参加者（チケット）ごとの属性で、fortee ユーザのプロフィールの値でも「名前」タイプのフォーム項目でもないこと、本番の本編では全参加者が未設定であることは確かめた（[data-model.md](data-model.md)） | Name をチケットごとに持ち、空なら表示しない（PRD 7.1、Design Doc 4.3）。検索は Name を当てにしない（PRD 11 章） |
| 本番の懇親会の I, J, K のチケット種別名（本編と懇親会の L のように【懇親会】が名前に付くか）（[data-model.md](data-model.md)） | 設定に書く種別名は、取り込んだスナップショットの値と照らして書く。スナップショットにない種別名は公開時に警告する（Design Doc 9.4） |
| 本番のダウンロード ZIP の容量（アバター画像を含むため、Sandbox の値から推定しかできていない）と、ダウンロード画面の設定でアバター画像を除けるか | 取り込みでは CSV と `qr-profile/` 以外を捨てる |
| 一括チェックイン CSV にキャンセル済の参加者の profile_url_token を書いたときの挙動 | キャンセル済の参加者はスナップショットになく、CSV にも含めない（FR-45）。書き出しの前に全イベントを取り込み直す（PRD 9 章の 6）ので、受付の間にキャンセルされた参加者もスナップショットから外れる。取り込み直してからアップロードするまでの間にキャンセルされた参加者の行は、CSV に残りうる |
| fortee のユーザ名（CSV の `User name`）が fortee 全体で一意か、退会や変更の後に別人が同じユーザ名を取れるか（再利用）、参加者が変更できるか、変更すると以後の CSV に新しい名前が出るか | ユーザの同一性はユーザ名の一致で判定する（FR-12）ので、同名の別人が同じカンファレンスの参加者にいれば同じユーザとして扱われる。一意でなければ、ユーザの同一性の判定を見直す。イベントごとの取り込みの時点がずれると、その間に名前を変えた参加者のチケットが別のユーザに分かれ、所持が必須のイベントの判定に失敗しうる。全イベントの ZIP を同じ作業で取り込んでまとめて公開する（PRD 9 章）。変更できるなら、受付期間中の変更は防げない運用上の制約として扱う。実装の初めに fortee の画面で確かめる（Design Doc 12.3） |
| チェックイン API に `used` を再送したとき日時が更新されるか | チェックイン API は使わない |
