# 独自チェックイン機構に効く fortee 側の制約

fortee のチケット QR を読み取り、独自のルールでチェックインを判定し、結果を fortee に反映する仕組み（[PRD](../../prd.md)）を作るときに、fortee 側の仕様から生じる制約をまとめる。各項目は、事実と、そこから導かれる制約の組で書く。根拠となる仕様は同じディレクトリの各ファイルにあり、PRD で決めた扱いは要件番号で示す。

## 1. 外部のオリジンから fortee を呼ぶこと

**確認した対象では、外部のオリジンから fortee を利用できなかった。** 次のとおり確かめた。Sandbox は非表示設定のため未ログインのリクエストには「Conference not found」の 404 しか返さず、ヘッダの確認には使えなかったので、ヘッダは本番の公開ページと管理画面パスで見ている。

| 確認 | 結果 |
| --- | --- |
| 本番に未ログイン・`Origin: https://example.org` 付きで GET（公開トップ、参加者一覧 API、一覧の HTML 断片、チェックイン状態取得 API、一括チェックイン画面） | どの応答にも `Access-Control-Allow-Origin` がない。管理画面パスは `/login?redirect=...` へ 302、参加者一覧 API は 404（API有効がオフのためと推定） |
| 本番のチェックイン状態取得 API に `OPTIONS` でプリフライト | CORS ヘッダなしで `/login` へ 302 |
| ログイン済みの Chrome で `https://example.com` から Sandbox の参加者一覧 API とチェックイン状態取得 API を `fetch`（`credentials: include` と `omit` の両方） | いずれも `TypeError: Failed to fetch` で失敗する |

確かめたのは表の対象だけである。未ログインの応答には `Access-Control-Allow-Origin` がなかったが、管理画面のパスと API の応答は `/login` への 302 か 404 で、データを返す応答ではなかった。ログインした状態の `fetch` は `Failed to fetch` で失敗し、失敗の理由と応答のヘッダはページから見えない。したがって、この結果から言えるのは、fortee 以外のオリジンで配信するブラウザアプリが、ログイン済みの Cookie があっても、表の対象からデータを読めず、チェックイン状態取得 API も呼べなかったことまでである。表にないエンドポイントと、ログインした状態の応答が CORS ヘッダを持つかは確かめていない。

ファイルを介する連携を採るのは、この結果だけによるのではない。ブラウザから呼べるエンドポイントがあったとしても、受付アプリとサーバに fortee の認証情報を置かない（NFR-7）ので使わず、公開仕様でない管理画面の API にも依存しない。取り込みと反映は、管理者が fortee からダウンロードした ZIP と、管理者が fortee にアップロードする一括チェックイン CSV という、ファイルを介して行う。fortee のセッションを持つ中継サーバを置く方法もあるが、スタッフの Cookie をサーバに預けることになり、fortee 側の変更にも追随が要るので採らない（NFR-7）。

## 2. QR の読み取り

**チェックイン用 QR の内容は `fortee:` + 32 文字のチケットトークン（計 39 文字）で、固定長の ASCII である。** 画面でもウォレットでも同じ文字列である。読み取った文字列の検証は「`fortee:` で始まり、残り 32 文字が英数字」で足りる（FR-11）。fortee が描く画像はバージョン 3・誤り訂正 M（29×29 モジュール）で、参加者のチケット画面では 120px の `<img>` で表示される。ウォレットではシンボルをウォレット側が描く（[qr-code.md](qr-code.md)）。

**fortee は同じ参加者に対して URL 形式の QR も発行している。** フィードバック QR（チケット詳細 URL）とプロフィール QR（go-profile URL）で、名札用の PDF に印字されるのは後者である。読み取り結果が `https://fortee.jp/` で始まるときはこれらであり、チケット QR ではない（FR-11 の形式外）。フィードバック QR の URL はチケットトークンを含むのでチケットを特定できるが、プロフィール QR は profile_url_token なので、profile_url_token から参加者を引ける索引がないと特定できない。受付アプリは、どちらもチケット QR ではないとして扱う。

**トークンは英数字の大文字小文字を区別するものとして扱う。** 大文字と小文字だけが異なるトークンが衝突するかは検証していないが、正規化で大文字化・小文字化しない。

## 3. 識別子と同一人物の判定

**参加者はチケット 1 枚につき 1 行で、同一人物の判定は fortee のユーザ（ハンドル名）で行われている。** 「前夜祭チケットの読み取りで本編チケットも同時にチェックインする」のような判定は、チケットトークン → 参加者 → ユーザ → そのユーザの全参加者、という辿り方で実現する（FR-12）。ユーザを跨いだ紐付け（同行者など）は fortee のデータにはない。

**チケット間の依存関係は、fortee ではチケット種別の「前提条件」として設定されている。** この設定は参加者データのどの経路にも出ないので、独自システムの受付の設定（FR-2 の所持が必須のイベント）として持ち込む。fortee 自身はこの依存関係を購入時にしか見ず、本編チケットを後からキャンセルしても前夜祭チケットは残る（[data-model.md](data-model.md)）。独自システムでは、この整合を判定し直さない。

**1 人が同じイベントのチケットを複数枚持つことがある。** 本番では前夜祭チケットを 3 枚持つユーザや、一般チケットをキャンセルしてスピーカーチケットに移ったユーザがいる。ルールは「ユーザが本編チケットを持つか」ではなく「ユーザの有効なチケットのうち、どれをチェックイン済みにするか」まで決める必要がある（FR-15, 26）。

**未発券の参加者は、発券されると同じ行が埋まる。** 参加者 ID・両トークン・チェックイン状態は維持され、ユーザ・メール・フォーム回答が後から入る。未発券の行はダウンロード ZIP にも含まれる（User name と Issued が空）ので、取り込みで除外する（FR-43）。再取り込みの突合キーにはチケットトークンを使えば、未発券の行に発券が入っても記録が引き継がれる。fortee の参加者 ID はダウンロード CSV に含まれないので、キーには使えない。

**参加者 ID、チケット ID、チケット番号、チケットトークン、profile_url_token は別物である。** 独自システムの主キーにはチケットトークンを使い（PRD 7.1）、チケット番号は表示用にとどめる（プレフィックス変更で将来の採番が変わりうる）。チケットトークンと profile_url_token を取り違えると、fortee への反映が「Attendee not found」で失敗する。

**フォーム回答（購入時アンケート）は、ダウンロード CSV に項目名の列として入る。** 受付で参照したい回答は、取り込み時に列名で選んで最小データに含める（FR-1, 43）。列名は fortee 上の項目名そのものなので、項目名を変えると取り込みが壊れる。取り込みでは列の存在を検証し、なければ止める（FR-43）。参加者一覧 API にも回答は出るが、参加者 ID やチケット番号がなく突合できないので使わない。

## 4. 参加者データの取り込み

**fortee に、必要な情報をすべて 1 回で返す API はない。** 参加者一覧 API はフォーム項目しか返さず、ダウンロード CSV にはキャンセル済と profile_url_token とチェックイン日時がなく、一覧の HTML 断片には profile_url_token がない（[data-sources.md](data-sources.md)）。独自システムはダウンロード ZIP を基本にし、CSV の Ticket url からチケットトークンを、`qr-profile/` 画像のデコードから profile_url_token を得る（FR-43）。キャンセル済は含まれないので「CSV にない参加者は無効」と扱う（FR-17）。

**ダウンロード ZIP は、参加者 1 人あたり数 KB である。** Sandbox の参加者 1 人分の内訳は次のとおりだった。本番規模（本編の参加者一覧 750 行）でも、画像を除けば数 MB にとどまる。

| 項目 | サイズ |
| --- | --- |
| CSV 1 行（ヘッダ込み） | 約 500 バイト |
| `qr-profile/` の PNG（482×482、バージョン 6・誤り訂正 M） | 約 2.9 KB |
| `qr-feedback/` の PNG（同上） | 約 2.9 KB |
| ZIP 全体 | 約 4 KB（圧縮後） |

ZIP には `avatar/` ディレクトリもある。Sandbox ではアバター未設定で空だったが、本番ではユーザごとのアバター画像が入るため、画像 1 枚あたり数十 KB として本番の ZIP は数十 MB になりうる（推定）。ダウンロード画面の「出力フィールド」で CSV の列は絞れるが、画像の有無を制御できるかは未確認である。取り込みでは、CSV と `qr-profile/` 以外は捨ててよい。

**`qr-profile/` の画像は、バージョン 6（41×41 モジュール）、誤り訂正 M の素直な QR である。** qrtool と Chrome の BarcodeDetector の両方で読めた。純 JavaScript のデコーダ（jsQR など）で機械的にデコードするのが、profile_url_token を全参加者分そろえる最も手間の少ない方法である。ZIP のエントリ名は日本語（チケット種別名）を含むが、UTF-8 フラグ（汎用ビット 11）付きで格納されており、CSV の「QR profile filename」列の値と一致する。使う ZIP ライブラリがこのフラグを尊重するかは実装時に確かめる。

**一覧の HTML 断片にはキャンセル・完全削除のフォームが含まれる。** HTML 断片を解析するコードを書く場合は、フォームの送信やリンクの自動追従を行わないようにする。本番で誤って POST すると参加者が消える。

**ダウンロード CSV の列も、管理画面の HTML 構造も、公開仕様ではない。** 予告なく変わりうるので、取り込み処理は列名を検証し、想定外なら止まるようにする（FR-43）。

**スナップショットは古くなる。** スピーカー・スポンサーの追加、キャンセル、未発券の引き当ては開催直前まで起こる。取り込み日時を版として記録し（FR-44）、受付前日と、各受付の終了後の書き出しの前に再取り込みする（PRD 9 章）。

## 5. チェックイン状態の整合

**fortee 側にもチェックイン状態があり、標準の読み取り画面・手動チェックイン・一括チェックインのどれでも変わる。** 独自システムを正とするので、受付期間中は fortee 側の操作を使わず、受付終了後に独自システムの状態を反映する（PRD 9 章）。両方を使うと、どちらが正しいかが分からなくなる。fortee 側でだけ済みになっているチケットは、独自システムでは未チェックインとして扱い、参考表示にとどめる（FR-16）。

**fortee は「イベントごと・チケットごと」に 1 つの日時を持つだけで、受付の種類は表現できない。** 独自システム側で「どの受付で、どのチケットを、どの経路・理由で済みにしたか」を持ち（FR-39）、fortee には結果だけを反映する。

**fortee の日時は分単位で表示され、CSV の `checkined_at` は秒・タイムゾーン付きで受け付ける。** タイムゾーンなしで書くと JST と推定されるので、設定のタイムゾーンのオフセット付き ISO 8601 で書く（PRD 7.3）。

## 6. fortee への反映

**一括チェックイン CSV は「済みにする差分」だけを適用し、未チェックインに戻せない。** 誤って fortee 側で済みになった参加者を戻すには、チェックイン API で `unused` を送るか手動解除する。書き出しには「fortee 側でだけ済みの参加者」の一覧を含め（FR-45）、管理者が個別に戻せるようにする。

**CSV のキーは profile_url_token である。** QR から得たチケットトークンでは反映できないので、取り込み時に profile_url_token を全参加者分そろえておく（FR-43）。

**同じ参加者を含む CSV を再アップロードすると日時が上書きされ、空欄だとアップロード時刻になる。** 空欄は使わず、同じ参加者には常に同じ日時（PRD 7.2 で求めた時刻）を書き、参加者 1 人につき 1 行にする（PRD 7.3）。

**存在しないトークンの行は失敗として報告され、他の行は処理される。** アップロード後の「成功 n 件 / 失敗 m 件」と行ごとの結果を保存し、失敗行を再確認する。行数の上限は未確認なので、分割アップロードできる形で書き出す（FR-45）。

**チェックイン API は、イベント ID ごとのエンドポイントに、ログインセッション付きで 1 件ずつ呼ぶ。** 失敗時も HTTP 200 なので `result` で判定する。日時は呼び出し時刻になるので、受付時刻を残すには CSV を使う。独自システムは、fortee の認証情報を置かない（NFR-7）ので、この API を使わない。

## 7. QR を持たない人の代替チェックイン

**チケット番号はイベント内でほぼ一意で、名前・所属などの回答は CSV にある。** fortee の採番が同じ番号を 2 人に付けることがあり（[data-sources.md](data-sources.md)）、そのときは検索に同じ番号のチケットが複数出る。 QR を持たない来場者を、チケット番号、fortee のユーザ名、フォームの回答で検索し、スタッフの判断でチェックインする機能は、取り込んだデータだけで実現できる（FR-24〜26）。結果は通常のチェックインと同じ記録（チケット単位）になるので、反映 CSV に区別は要らない。

**本人確認に使える項目は、取り込んだ回答に限られる。** メールアドレスは CSV に出ない。フォームの名前は自由記述で表記ゆれ（姓名の順、スペース、漢字・かな）があるので、検索は部分一致と正規化で行い、一致判定は人が行う（FR-24）。

**未発券の参加者は検索で見つからない。** ユーザも回答もないので、チケット番号しか手がかりがない。未発券のまま来場する人がいない運用を前提にし、未発券はスコープ外とする（PRD 3.2）。

**代替チェックインで持ち込む回答は必要最小限にする。** 検索・照合に使う項目だけを最小データに含め、住所・電話番号のような項目は端末に置かない（PRD 7.1）。

## 8. 運用とセキュリティ

**本番カンファレンスで試験操作をしない。** QR 生成、バルク削除、キャンセル、完全削除、一括チェックインはすべて本番データを変える。fortee の挙動を確かめる検証は Sandbox で行う。受付アプリの運用の開始（PRD 9 章の 2）で行うスタッフのチケットの受付は、試験操作に当たらない。本番のチケットを受付と同じ手順で受け付け、その記録を本番に一括チェックインする。

**チケットトークンを知っていれば、ログインなしでチケット詳細 URL を開ける。** 本番のチケット詳細 URL に未ログインで GET すると 200 が返った（ヘッダのみ確認。表示内容は未確認）。トークンは本人確認なしで使える値として扱い、スナップショットは受付スタッフの認証の内側にだけ置く（PRD 7.1）。保存する参加者データは受付に必要な範囲にとどめ、メールや選んでいない回答は持ち込まない。端末のデータはログアウトで消す（FR-37）。

**fortee のセッションは管理画面用の Cookie である。** 反映を手動の CSV に限定すれば、受付端末もサーバも fortee の認証情報を持たずに済む（NFR-7）。

**会場のネットワークは当てにしない。** 独自システムは取り込んだスナップショットだけで判定・記録できるようにし（NFR-2）、fortee との通信は取り込みと反映の 2 回に限る。
