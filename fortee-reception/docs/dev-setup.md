# 開発・環境構築手順書

本書は、fortee 連携チェックインシステムを開発し、カンファレンスの環境を運用して削除するまでの手順を定める。対象は、開発に要る道具、依存関係の導入、ローカルでの起動とテスト、運用の開始、運用の開始後のデプロイ、秘密の扱い、保持期間の後の削除である。カンファレンスの環境を作る手順は、[本番環境構築手順書](production-setup.md)に分けてある。

手順の前提になる設計は [Design Doc](design-doc.md) にあり、本書は繰り返さない。環境とその構成要素の対応は Design Doc 3.6、管理 CLI のコマンドは 8.1、版と互換性は 9.5〜9.7 にある。受付の運用の手順（準備、運用の開始、直前、端末の準備、受付中、終了後）は [PRD](prd.md) 9 章にある。

本書のコマンドは、Design Doc 3.4 のリポジトリの構成と 8.1 の CLI を前提にしている。実装と、構築の最初に確かめること（Design Doc 12 章、[バックエンド](research/backend.md) 8 章、[フロントエンド](research/frontend.md) 7 章）の結果に合わせて、本書を直す。

コマンドは、リポジトリの `fortee-reception/` で実行する（Design Doc 3.4）。

2026-11-12 の時点で、受付アプリ、Worker、管理 CLI のすべてのコマンドを実装してある。確かめてあるのは、ローカルでの型検査、lint、単体テスト、画面のテスト（4.4）までである。本番環境構築手順書と 6 章以降の手順（カンファレンスの環境の作成、リモートの D1 と KV への操作、デプロイ、Discord の実際のログイン）は、まだ実行していない。実機での確認と、本物の fortee の ZIP の取り込みも、まだである。実行して手順と食い違うところが見つかれば、本書を直す。

## 1. 用語

| 用語 | 意味 |
| --- | --- |
| 環境 | 1 つのカンファレンスのための Worker、D1、KV、秘密、設定ファイル、作業ディレクトリの組（Design Doc 3.6） |
| 環境名 | 環境の名前。そのカンファレンスの fortee のスラッグ（例 `yapc-tokyo-2026`）。ローカルの開発は `local` |
| 運用の開始 | その環境に本番の設定と本番の ZIP を公開し、本番のチケットの受付を始める時点。この時点から保持期間の後の削除まで、記録を消さず、D1 を作り直さない（Design Doc 3.6） |
| 確認用の環境 | 開発と実機の確認のために、Sandbox のカンファレンス用に作る環境。作らなくてもよい（Design Doc 3.6） |
| 環境の印 | D1 と KV に置く環境名。`migrate` が書き、CLI のコマンドが `--env` と照合する（Design Doc 3.6、8.1） |

## 2. 必要なもの

| 対象 | 用途 | 備考 |
| --- | --- | --- |
| Node.js（LTS） | ビルド、テスト、管理 CLI、wrangler | 版は `package.json` の `engines` と `.node-version` で固定する。wrangler と Vite が求める版を満たすものとして、26.13.0 を選んだ（`engines` は `^26.13.0`）。管理 CLI は、この Node.js が TypeScript をそのまま実行する（Design Doc 3.2） |

| Cloudflare のアカウントと API トークン | 環境の作成、デプロイ、管理 CLI | トークンの権限はバックエンド 4 章のとおり、操作ごとに絞る。4 章の表にない操作では、D1 と KV の作成とマイグレーションに D1 と Workers KV Storage の Edit、デプロイと秘密の設定に Workers Scripts の Edit を付ける（ほかに要る権限は、環境を作るときに確かめる）。トークンには、作る管理者のメンバーのロールが持つ権限までしか付けられないので、管理者には、これらの権限を含むロールを与えておく。Workers Platform Admin で足りる（バックエンド 4 章）。`wrangler login` は使わない。`--scopes` で OAuth のスコープを選べるが、API トークンなら、D1 と KV の読み取りだけの権限と編集の権限を、操作ごとに作り分けられる（バックエンド 4 章）。`--scopes` で同じ粒度に絞れるかは確かめていない |
| Discord のアプリケーションとギルド | ログイン | カンファレンスの環境とローカルの開発で、同じものを使う（Design Doc 3.6） |
| デスクトップの Chrome | ローカルでの確認 | Playwright のブラウザは、これとは別に入れる（3 章） |
| iPhone と Android の端末 | 実機での確認 | ローカルではなく、デプロイした環境（カンファレンスの環境か、確認用の環境）で確かめる。運用を始めた後の環境で試したチェックインは、本番の記録として残る（Design Doc 3.6） |

## 4. ローカルでの開発

ローカルの開発は、どのカンファレンスの環境とも接続しない（Design Doc 3.6）。開発サーバは `wrangler.jsonc` の最上位の設定で動き、D1 と KV はローカルの模擬環境（`.wrangler/state` 以下）を使う。

### 4.1 ローカル用の秘密

1. 本番と同じ Discord のアプリケーションに、リダイレクト URI `http://localhost:5173/auth/discord/callback` を加える。ポートは Vite の開発サーバのもの
2. `.dev.vars.example` を `.dev.vars` に写し、値を書く

| 名前 | 値 |
| --- | --- |
| `DISCORD_CLIENT_ID`、`DISCORD_CLIENT_SECRET` | 本番と同じ Discord のアプリケーションの値 |
| `DISCORD_GUILD_ID`、`DISCORD_ROLE_IDS` | 本番と同じギルドと、受付スタッフのロール（カンマ区切り）。ログインする開発者も、そのロールを持つ |
| `SESSION_SECRET` | 暗号論的疑似乱数で生成した 32 バイトの値。たとえば次のコマンドで作る |

```bash
openssl rand -base64 32
```

`.dev.vars` には本番と同じクライアントシークレットが入る。開発者は手元の秘密を善良に管理することを前提とし、`.dev.vars` をコミットせず、ほかの場所に写さない（Design Doc 3.6）。

### 4.2 起動

ローカルの D1 にマイグレーションを適用してから、開発サーバを起動する。`migrate` は、ローカルの D1 と KV に環境の印（`local`）も書く。

```bash
npm run admin -- migrate --env local
```

```bash
npm run dev
```

`http://localhost:5173` を、デスクトップの Chrome で開く。Discord のログインと Cookie の扱いは、本番と同じ形で動く（Design Doc 3.5）。

### 4.3 ローカルへの取り込みと公開

ローカルの設定は `config/local.toml` に置く。スラッグは Sandbox のカンファレンスのもので、`conference.environment` は `local` にする。イベントとチケット種別は、合成の ZIP に合わせてあり、イベント ID も合成の値である。取り込む ZIP は、`test/cli/make-synthetic-zips.ts` で作る合成の ZIP を使う。合成の ZIP は、fortee の仕様調査の記述から作ったもので、Sandbox からダウンロードした ZIP ではない（`test/cli/synthetic-zip.ts` の冒頭）。本番の ZIP は参加者の情報を含むので、リポジトリに置かない。

```bash
npm run admin -- migrate --env local
```

```bash
node test/cli/make-synthetic-zips.ts
```

ZIP は `.work/local/synthetic-zips/` に、イベントごとに 1 つ（`main.zip`、`eve.zip`、`party.zip`）できる。

```bash
npm run admin -- validate --env local
```

```bash
npm run admin -- import --env local --event <イベントの key> --zip <ZIP のパス>
```

```bash
npm run admin -- publish --env local
```

### 4.4 テストと検査

```bash
npm test
```

```bash
npm run test:e2e
```

```bash
npm run typecheck
```

```bash
npm run lint
```

`npm test` は core、app、worker、cli の Vitest と、lint の規則が違反を検出することの検査（Design Doc 3.2）を、`npm run test:e2e` は Playwright の画面のテストを動かす。何を確かめるかは Design Doc 11 章にある。

`npm run test:e2e` は、サーバとデータを自分で用意する（`test/e2e/setup/serve.ts`）。開発の `.wrangler/state` と `.work/` には触れず、`.wrangler/e2e/` と `.wrangler/e2e-sync/` を毎回空にして、合成の ZIP とテスト用の設定（`test/e2e/fixtures/e2e.toml`）を公開し、ビルドの出力を `wrangler dev` でポート 4173 と 4174 に配る。4.3 の公開は要らない。セッションの秘密はテスト用の値を渡し、`.dev.vars` の値は使わない。Discord には通信しない。どちらかのポートをほかのサーバが使っていると、起動できずに止まる。QR の文字列を判定に渡すテスト用の入口（`window.__checkinTest`）は、このビルドと開発サーバ（`npm run dev`）にだけ入り、CLI の `deploy` のビルドには入らない。

GitHub Actions（リポジトリの直下の `.github/workflows/ci.yml`）は、`main` への push とプルリクエストで、3 章の導入と、この 4 つのコマンドを実行する。秘密は使わない。

見た目を確かめるスクリーンショットは、出力先を環境変数で渡したときだけ撮る。幅 390px の Chromium の分を撮る。

```bash
E2E_SHOTS=<出力先のディレクトリ> npm run test:e2e
```

## 5. カンファレンスの環境を作る

カンファレンスごとに 1 回行う。環境は、そのカンファレンスのためだけに作り、運用の開始（7 章）、受付、最終の書き出しを経て、保持期間の後に削除する（10 章）。前のカンファレンスの環境を使い回さず、カンファレンスごとに新しく作る（Design Doc 3.6）。

作る手順は、[本番環境構築手順書](production-setup.md)にある。API トークンと Discord のアプリケーションの用意から、D1 と KV の作成、`wrangler.jsonc` と設定ファイルの記述、マイグレーション、デプロイ、秘密の設定、データの公開、構築の確認までを扱う。以下の章が「本番構築」と書くときは、この文書の章を指す。

## 6. 運用を始める前

カンファレンスの環境は、運用を始めるまで、開発中の確認に使える。この間は、コードの変更を `deploy` でそのまま配ってよく、同期プロトコルの版、配布物の形式の版、IndexedDB の形、マイグレーションのファイルを変える変更も配ってよい（Design Doc 9.6）。Sandbox や合成の ZIP を取り込んで公開してもよい。公開して確認に使った環境は、運用の開始の前に D1 と KV を作り直し、端末をログアウトする（7 章の 2）。

開発と実機の確認には、確認用の環境を別に作って使ってもよい（Design Doc 3.6）。本番環境構築手順書の手順で、環境名を Sandbox のカンファレンスのスラッグにして作る。カンファレンスの環境に試験のデータを載せなければ、7 章の 2 の作り直しとログアウトは要らない。確認用の環境は、使い終えたら 10 章の手順で削除する。同じアカウントに残すと、要求数と D1・KV の日次の上限を、受付をする環境と分け合う（バックエンド 8.1）。

既存のマイグレーションのファイルを書き換えたときは、D1 を作り直す（Design Doc 9.6）。D1 を消して（10 章の 3 のコマンド）本番構築 3.2 で作り直し、`wrangler.jsonc` の ID を書き換え（本番構築 3.4）、`migrate` をやり直す（本番構築 5.1）。KV の環境の印は残り、作り直した D1 の印を `migrate` が書く。作り直した D1 には公開の版がないので、公開もやり直す（本番構築 6 章）。IndexedDB の形か配布物の形式を変える変更は、その環境で受付アプリを使っている端末をログアウトしてから配る（Design Doc 9.6）。

## 7. 運用の開始

運用を始めた後は、その環境の記録を消さず、D1 を作り直さない（Design Doc 3.6）。運用は、次の順に始める。

確認用の環境を別に作っていない場合は、先に、運用を始めると行えなくなる確認が済んでいることを確かめる。運用を始めた後の環境は記録を消さないので、D1 に試験の記録を書く確認と、DB を戻す試験には使えない（Design Doc 3.6、12.3）。対象は次のとおりである。

- Design Doc 12.2 の「SQL に渡す値」のうち、リモートの D1（`--remote`）での確認
- Design Doc 12.3 のうち、確かめる場が「運用の開始前か確認用の環境」の確認（同期の受信の文、`wrangler d1 execute --json` の結果の大きさと `RETURNING` の行、`wrangler rollback` と静的アセット、保持期間の後の削除のコマンド）
- バックエンド 8.1 の「DB を戻したときの回収」のうち、Time Travel で戻すリモートの D1 での確認

1. 運用に使うコードをコミットする。運用の開始から最終の書き出しまで、同期プロトコルの版、配布物の形式の版、IndexedDB の形、既存のマイグレーションのファイルは変えない（8 章）ので、これらを変える変更は、ここまでに入れておく。`deploy` は未コミットの変更があると止まり、デプロイの記録にはリリース名（`git describe`）が残る（Design Doc 8.1）。リリースに名前を付けるときは、コミットに `fortee-reception/v0.3.0` の形のタグを付ける。タグがなければ、リリース名はコミットの短いハッシュになる
2. その環境に Sandbox や合成のデータを公開して確認に使った場合は、そのオリジンで受付アプリを使った端末をログアウトしてから、D1 と KV を作り直す。D1 と KV を消して（10 章の 3 と 4 のコマンド）本番構築 3.2 と 3.3 で作り直し、`wrangler.jsonc` の ID を書き換える（本番構築 3.4）。端末をログアウトするのは、端末に試験の記録が残っているためである。作り直した D1 は DB の世代が変わり、端末は、世代の変化を知ると、持っている記録をすべて送り直す（Design Doc 3.6）
3. マイグレーションを適用し、デプロイする。`migrate` は、作り直した D1 と KV に環境の印を書く

   ```bash
   npm run admin -- migrate --env <環境名>
   ```

   ```bash
   npm run admin -- deploy --env <環境名>
   ```

4. 本番の設定（`config/<環境名>.toml`）で、全イベントの本番の ZIP を取り込んで公開する（本番構築 6 章）。運用を始めた後の環境には、Sandbox の設定と ZIP を公開しない（Design Doc 3.6）
5. スタッフの端末で受付アプリを開き、ログインする。2 でログアウトした端末も、ここでログインし直す。どの端末がどのリリースで同期したかは、書き出しの `devices.csv` で分かる
6. 来場者の受付の前に、スタッフ自身のチケットを受付と同じ手順で受け付け、書き出しと fortee への一括チェックインまでを通す（PRD 9 章の 2）。4 の公開の後の記録は消さない。誤ったチェックインは、取り消しで打ち消す。取り消さなかったチェックインは、書き出しから fortee に一括チェックインされ、一括チェックイン CSV では未チェックインに戻せない（[constraints.md](research/fortee/constraints.md) 6 章）

## 8. 運用の開始後のデプロイ

運用の開始から最終の書き出しまでは、同期プロトコルの版、配布物の形式の版、IndexedDB の形、既存のマイグレーションのファイルを変える変更をデプロイしない。端末に、更新前の受付アプリ、端末内のデータ、未同期の記録が残るためである（Design Doc 9.6）。これらを変えない修正（画面、判定の不具合、管理 CLI）と、マイグレーションの追加はデプロイできる。マージの前に、Design Doc 9.7 の表で、どの変更に当たるかを確かめる。デプロイは、マイグレーションを適用してから行う。

```bash
npm run admin -- migrate --env <環境名>
```

```bash
npm run admin -- deploy --env <環境名>
```

`deploy` は、デプロイしたリリース名を Workers の版の記録に残す。どのリリースが動いているかは、次のコマンドで確かめる。

```bash
npx wrangler deployments list --env <環境名>
```

同期プロトコルの版、配布物の形式の版、IndexedDB の形を、どうしても変える必要が出たときは、次の順に行う（Design Doc 9.6）。既存のマイグレーションのファイルは、この手順でも変えない。

1. 全端末を同期させ、各端末のヘッダが「同期済み」であることを確かめる。ログアウトは端末のデータを消すので、未同期の記録を残さない
2. 全端末をログアウトする
3. 版の値を上げた変更を、`migrate` と `deploy` でデプロイする。形式の版を変えたときは、続けて公開し直す（`publish`）
4. 各端末で受付アプリを開き直し、ログインする

前のカンファレンスの環境を操作するとき（保持期間の中の書き出しや復旧、保持期間の後の削除）は、その環境にデプロイしたコミットを別の作業ツリーに取り出し、そこから CLI を実行する（Design Doc 9.6）。

```bash
git worktree add ../checkin-<環境名> <コミット>
```

コードを戻すときは、Design Doc 9.7 の手順に従う。上の手順で形を変えたデプロイより前には戻さない。

## 9. 秘密の扱い

| 秘密 | 置き場所 | 扱い |
| --- | --- | --- |
| Discord のクライアントシークレット、ギルド ID、ロール ID、`SESSION_SECRET` | 環境ごとの Worker の secret。ローカルは `.dev.vars` | リポジトリに置かない（FR-5）。Discord の値はローカルも本番と同じで、開発者が善良に管理する（4.1）。名前は Design Doc 3.6 |
| Cloudflare の API トークン | 管理者の端末の環境変数 | 管理者ごとに、その管理者のロールが持つ権限のうち、操作に要る権限だけを持つものを作る（バックエンド 4 章）。リポジトリとシェルの履歴に残さない |
| 書き出しのファイル、取り込む ZIP、作業ディレクトリ（`.work/<環境名>/`） | 管理者の端末 | 参加者の情報を含む。リポジトリに置かず、保持期間（PRD 7.4）の後に消す（10 章） |

`SESSION_SECRET` を差し替えると、その環境の全端末が再ログインになる（Design Doc 7.2）。ロールを外したスタッフのセッションをすぐに止めたいときの手段であり、端末のデータは消えない。

## 10. 保持期間の後の削除

保持期間（PRD 7.4）が過ぎたら、その環境のサーバのデータと、管理者の端末に残したファイルを消す。環境は次のカンファレンスに使い回さない（Design Doc 3.6）ので、Worker、D1、KV を、資源ごと削除する。消す対象は Design Doc 8.9 にある。最終の書き出し、fortee の反映結果の確認、全端末のログアウト（PRD 9 章の 7）が済んでいることを、先に確かめる。サーバの削除は取り消せない。

1. API トークンを環境変数に置く（本番構築 3.1）。削除には、D1 と Workers KV Storage の Edit と、Workers Scripts の Edit が要る（バックエンド 4 章）。以下のコマンドは、対話できる端末で実行する。対話できない環境では、wrangler が確認を待たずに進んだことがある（バックエンド 7.2）
2. Worker を削除する。静的アセットと秘密も消える。先に `--dry-run` を付けて実行し、消す対象が `checkin-<環境名>` であることを確かめる

   ```bash
   npx wrangler delete --env <環境名> --config wrangler.jsonc --dry-run
   ```

   ```bash
   npx wrangler delete --env <環境名> --config wrangler.jsonc
   ```

3. D1 のデータベースを、名前を指定して削除する

   ```bash
   npx wrangler d1 delete checkin-<環境名> --env <環境名> --config wrangler.jsonc
   ```

4. KV の名前空間を、ID を指定して削除する。ID は、`wrangler.jsonc` のその環境の `kv_namespaces` に書いた値である

   ```bash
   npx wrangler kv namespace delete --namespace-id <KV の名前空間の ID> --env <環境名> --config wrangler.jsonc
   ```

   3 と 4 では、消す対象を名前と ID で指定する。`--env` と `--config` は、アカウント（その環境の `account_id`）を選ぶために付ける。コマンドの引数は Wrangler の文書で確かめた（2026-11-10）が、実行は確かめていない。確認の表示が出るかと、`--env` でその環境のアカウントが選ばれるかは、運用の開始の前に D1 を作り直すとき（6 章、7 章の 2）に、同じ形のコマンドで確かめておく

5. 管理者の端末から、作業ディレクトリ（`.work/<環境名>/`）、書き出しの出力、fortee からダウンロードした ZIP を消す。書き出しの出力には、途中で止まった書き出しが `--out` の親ディレクトリに残した一時ディレクトリを含む。複数の管理者が取り込みや書き出しをした場合は、管理者ごとに行う

   ```bash
   rm -rf .work/<環境名>
   ```

6. Discord のアプリケーションから、その環境のリダイレクト URI を外す。`wrangler.jsonc` の env のブロックと `config/<環境名>.toml` は、参加者の情報を含まないので、残してよい
