# 本番環境構築手順書

本書は、1 つのカンファレンスの受付に使う環境（本番環境）を、何もない状態から作り、スマートフォンでログインできることを確かめるまでの手順を定める。対象は、Cloudflare のアカウントと API トークンの用意、Discord のアプリケーションの用意、D1 と KV の作成、`wrangler.jsonc` と設定ファイルの記述、マイグレーション、デプロイ、秘密の設定、データの公開、構築の確認である。

本書が扱うのは、環境を作るところまでである。作った環境で本番のチケットの受付を始める手順（運用の開始）、運用の開始後のデプロイ、保持期間の後の削除は、[開発・環境構築手順書](dev-setup.md)の 6 章以降にある。受付の運用の手順は [PRD](prd.md) 9 章にある。

手順の前提になる設計は [Design Doc](design-doc.md) にあり、本書は繰り返さない。環境とその構成要素の対応は Design Doc 3.6、設定ファイルの書き方は 4.2、管理 CLI のコマンドは 8.1 にある。Cloudflare の権限と構築の注意は[バックエンド](research/backend.md)の 4 章と 8 章にある。本書と Design Doc が食い違う場合は Design Doc に従い、本書を直す。

コマンドは、リポジトリの `fortee-reception/` で実行する。

2026-11-12 の時点で、本書の 3 章以降の手順は、まだ実行していない。確かめてあるのは、管理 CLI のコマンドの動きを実装で読んだことと、wrangler のコマンドと引数が、導入してある wrangler 4.157.0 のヘルプにあることまでである。wrangler の出力の内容、Cloudflare のダッシュボードと Discord の画面での操作、権限の過不足は確かめていない。実行して手順と食い違うところが見つかれば、本書を直す。

開発と実機の確認のための確認用の環境（Design Doc 3.6）も、環境名を Sandbox のカンファレンスのスラッグにして、同じ手順で作る。

## 1. 作るものと、作る順序

環境は、1 つのカンファレンスのための Worker、D1、KV、秘密、設定ファイル、作業ディレクトリの組である（Design Doc 3.6）。環境名（そのカンファレンスの fortee のスラッグ）を 1 つ決めると、残りの名前が決まる。

| 作るもの | 名前 | 作る場所 | 章 |
| --- | --- | --- | --- |
| D1 のデータベース | `checkin-<環境名>` | Cloudflare | 3.2、3.5 |
| KV の名前空間 | `checkin-<環境名>` | Cloudflare | 3.3 |
| wrangler の env | `env.<環境名>` | `wrangler.jsonc` | 3.4 |
| 設定ファイル | `config/<環境名>.toml` | リポジトリ | 4 章 |
| Worker | `checkin-<環境名>` | Cloudflare（`deploy` が作る） | 5.2 |
| Worker の秘密 | `DISCORD_CLIENT_ID` など 5 つ | その Worker の secret | 5.3 |
| リダイレクト URI | `<オリジン>/auth/discord/callback` | Discord の開発者画面 | 5.4 |
| 作業ディレクトリ | `.work/<環境名>/` | 管理者の端末（`import` が作る） | 6 章 |

オリジンは `https://checkin-<環境名>.<アカウントのサブドメイン>.workers.dev` である。スタッフの端末を準備する前に決め、以後は変えない（バックエンド 2.2）。

作る順序は、3 章から 7 章の章の順である。順序を入れ替えられないのは、次の 3 か所である。

- `migrate` は、D1 と KV に触れるほかのどの CLI のコマンドよりも先に実行する。`migrate` だけが環境の印を書き、ほかのコマンドは、印がないと止まる（Design Doc 8.1）
- `deploy` は、`wrangler.jsonc` と設定ファイルをコミットした後に実行する。`deploy` は設定ファイルを読んでビルドし、`fortee-reception/` 以下に未コミットの変更があると止まる（Design Doc 8.1）
- 秘密の設定は、`deploy` の後に行う。秘密は Worker に付くものである。Worker がまだないときの `wrangler secret put` の動きは、確かめていない

環境は、カンファレンスごとに新しく作る。前のカンファレンスの環境を使い回さない（Design Doc 3.6）。

## 2. 構築の前に決めることと、用意するもの

### 2.1 環境名と Cloudflare のアカウント

環境名は、そのカンファレンスの fortee のスラッグにする（例 `yapc-tokyo-2026`）。使える文字は英小文字、数字、`-` で、55 文字までである。Worker の名前（`checkin-<環境名>`）の上限が 63 文字のためである。

Cloudflare のアカウントは、環境ごとに指定する。ほかの環境やほかのプロジェクトと同じアカウントにすると、Worker の要求数と D1・KV の日次の上限を分け合い、API トークンもアカウントの全 D1 と全 KV を操作できる（Design Doc 3.6、バックエンド 4 章）。同じアカウントにするときは、受付の期間にほかの Worker が要求数を使わないことを確かめる（バックエンド 8.1）。

Workers のサブドメイン（`<サブドメイン>.workers.dev`）は、アカウントに 1 つである。ダッシュボードで確かめ、オリジンを控える。

### 2.2 管理者のロールと API トークン

管理者は、そのアカウントのメンバーとして、Workers Platform Admin のロールを持つ（バックエンド 4 章）。ユーザの API トークンには、作るメンバーのロールが持つ権限までしか付けられないためである。

API トークンは、管理者ごとに、ユーザの API トークンとして作る。構築に使うトークンには、次の権限を付ける。

| 権限 | 使う操作 |
| --- | --- |
| D1 の Edit | D1 の作成、マイグレーション、公開 |
| Workers KV Storage の Edit | KV の作成、環境の印、公開 |
| Workers Scripts の Edit | デプロイ、秘密の設定 |

ほかに要る権限があるかは、まだ確かめていない。3 章から 6 章のコマンドが権限の不足で止まったら、止まった操作に要る権限を足し、本書の表を直す（バックエンド 8.1）。

`wrangler login` は使わない。API トークンなら、構築の後の操作（書き出しは D1 と KV の Read だけで足りる）に合わせて、権限を絞ったトークンを作り分けられる（バックエンド 4 章）。

### 2.3 Discord のアプリケーションとギルド

ログインには、Discord のアプリケーション 1 つと、受付スタッフのロールを持つギルドを使う。すべての環境とローカルの開発で、同じアプリケーションとギルドを使う（Design Doc 3.6）。まだなければ、Discord の開発者画面でアプリケーションを作る。

次の 4 種の値を控える。5.3 で Worker の秘密に入れる。

| 値 | 取り方 |
| --- | --- |
| クライアント ID | 開発者画面の、そのアプリケーションの OAuth2 の画面 |
| クライアントシークレット | 同じ画面で発行する。発行し直すと、ローカルの開発を含むすべての環境の値が古くなる |
| ギルド ID | Discord のアプリで開発者モードを有効にして、サーバの ID をコピーする |
| 受付スタッフのロール ID | 同じく、ロールの ID をコピーする。複数あるときは、カンマで区切って並べる |

受付アプリが求めるスコープは `identify` と `guilds.members.read` で、Bot をギルドに入れる必要はない。ギルド ID とロール ID は、設定ファイルに書かない（FR-5）。

### 2.4 手元の準備

開発・環境構築手順書の 2 章の道具（Node.js 26.13.0、npm、Git）をそろえ、3 章の導入を済ませる。

```bash
npm ci
```

デプロイするコミットで、開発・環境構築手順書 4.4 の検査とテストが通ることを確かめておく。

fortee から、イベントごとの ZIP をダウンロードしておく（PRD 9 章の 1）。運用を始める前の確認に Sandbox のデータを使うときは、6 章の注意を先に読む。

## 3. Cloudflare の資源を作る

### 3.1 API トークンを環境変数に置く

シェルの履歴に残さないよう、値は入力して読み込む。

```bash
read -s CLOUDFLARE_API_TOKEN && export CLOUDFLARE_API_TOKEN
```

3.2 と 3.3 のコマンドは、`wrangler.jsonc` にその環境のブロックを足す前に実行するので、アカウントを設定から決められない。トークンが複数のアカウントに届くときは、対象のアカウント ID も環境変数に置く。

```bash
export CLOUDFLARE_ACCOUNT_ID=<アカウント ID>
```

### 3.2 D1 を作る

```bash
npx wrangler d1 create checkin-<環境名> --location apac
```

設定ファイルに足すかを聞かれたら断り、出力された `database_id` を控える。足すと、コードが使わない名前のバインディングが増える（バックエンド 8.2）。

### 3.3 KV を作る

```bash
npx wrangler kv namespace create checkin-<環境名>
```

D1 と同じく、設定ファイルに足すかを聞かれたら断り、出力された `id` を控える。

### 3.4 `wrangler.jsonc` に環境を足す

`wrangler.jsonc` の `env` に、環境名のブロックを足す。`d1_databases` と `kv_namespaces` は最上位から引き継がれないので、環境ごとに書く。

```jsonc
"env": {
  "<環境名>": {
    "name": "checkin-<環境名>",
    "account_id": "<アカウント ID>",
    "d1_databases": [
      {
        "binding": "DB",
        "database_name": "checkin-<環境名>",
        "database_id": "<3.2 で控えた D1 の ID>",
        "migrations_dir": "migrations"
      }
    ],
    "kv_namespaces": [{ "binding": "KV", "id": "<3.3 で控えた KV の名前空間の ID>" }]
  }
}
```

最上位の設定は、ローカルの開発用なので書き換えない。最上位の D1 と KV の ID は実在しない仮の値で、`--env` を付け忘れた wrangler のコマンドは、どのカンファレンスの D1 と KV にも届かずに失敗する（Design Doc 3.6）。

ID を別の環境のものと写し間違えても、5.1 の `migrate` より後のコマンドは、環境の印の照合で止まる（Design Doc 3.6）。ただし、印のない D1 と KV には `migrate` が印を書くので、ここで ID を見比べておく。

3.1 で `CLOUDFLARE_ACCOUNT_ID` を置いたときは、ここで外す。以後は、アカウントを `account_id` から決める。

```bash
unset CLOUDFLARE_ACCOUNT_ID
```

### 3.5 D1 の主インスタンスの位置を確かめる

マイグレーションの前に、D1 の主インスタンスの位置を確かめる（バックエンド 8.1）。次のコマンドの出力の `meta.served_by_region` が APAC であることを見る。APAC でなければ、D1 を消して 3.2 から作り直す。

```bash
npx wrangler d1 execute DB --env <環境名> --remote --json --command "SELECT 1"
```

## 4. 設定ファイルを書く

`config/<環境名>.toml` を作る。書き方と、YAPC::Tokyo 2026 の例は Design Doc 4.2 にある。`config/local.toml` は合成の ZIP に合わせたローカル用の設定なので、写して使うときは、イベント ID、チケット種別名、受付の期間を本番の値に書き換える。

次の 2 つは、構築の手順に関わる。

- `conference.environment` に環境名を書く。CLI の `--env` と一致しなければ、どのコマンドも止まる
- `events` には、受付で扱わないイベント（託児所など）も含めて、そのカンファレンスの fortee のイベントをすべて書く（PRD 9 章の 1）

書いたら、検証する。`validate` は D1 と KV に触れないので、この時点で実行できる。誤りがあれば、すべて列挙される。

```bash
npm run admin -- validate --env <環境名>
```

## 5. マイグレーション、デプロイ、秘密

### 5.1 マイグレーションを適用する

```bash
npm run admin -- migrate --env <環境名>
```

`migrate` は、D1 にマイグレーションを適用し、D1 と KV に環境の印（環境名）を書く。wrangler が適用の確認を求めるので、対話できる端末で実行する。確認で取り消すと、`migrate` は印を書かずに止まる。

### 5.2 コミットして、デプロイする

`wrangler.jsonc` と `config/<環境名>.toml` をコミットする。`deploy` は、`fortee-reception/` 以下に未コミットの変更（追跡していないファイルを含む）があると止まる。

```bash
npm run admin -- deploy --env <環境名>
```

`deploy` は、受付アプリ、Service Worker、Worker をその環境に向けてビルドし、デプロイする。`vite build` と `wrangler deploy` を、手で分けて実行しない。デプロイの記録には、リリース名（`git describe`）が残る。リリースに名前を付けるときは、コミットに `fortee-reception/v0.3.0` の形のタグを付けてからデプロイする。タグがなければ、リリース名はコミットの短いハッシュになる（Design Doc 8.1）。

デプロイの出力かダッシュボードで、Worker のオリジンが 2.1 で控えたものと同じであることを確かめる。

#### 公開リポジトリにコミットする値

このリポジトリは公開するので、コミットした `wrangler.jsonc` と設定ファイルは、誰でも読める。どちらにも秘密は入らない。

| ファイル | 入る値 | 読まれたときにできること |
| --- | --- | --- |
| `wrangler.jsonc` | アカウント ID、D1 の ID、KV の名前空間の ID、Worker の名前 | これらの値だけでは、D1 と KV を読み書きできない。読み書きには API トークンが要る |
| `config/<環境名>.toml` | fortee のイベント ID、チケット種別名、アンケートの項目名、受付の期間、案内の文言、参考情報テンプレート | 受付の体制が分かる。参加者の情報は入らない |

Discord のクライアントシークレット、ギルド ID、ロール ID、`SESSION_SECRET` は、Worker の secret と `.dev.vars` にだけ置き、どちらのファイルにも書かない（FR-5）。設定ファイルには、公開したくない項目名や文言を書かない。

公開によって受け入れることは、オリジンを推測されやすくなることである。Worker の名前（`checkin-<環境名>`）が分かるので、アカウントのサブドメインを知る者は、オリジンに要求を送れる。記録と参加者の情報は、Discord のロールを持つアカウントでログインしなければ読めない。一方、ログインしていない要求も Workers Free の日次の要求数に数えられるので、外部から要求を送り続けられると、上限に達して同期が止まる。受付は端末内で続く（バックエンド 7.1）。受付中に使用量を見る担当者と、Workers Paid に切り替える条件を、受付の前に決めておく（バックエンド 8.1）。

環境のブロックと設定ファイルを公開したくないときは、push しないローカルのブランチにだけコミットし、そこからデプロイする。その場合、ほかの管理者には、そのブランチを別の経路で渡す。

### 5.3 Worker の秘密を入れる

秘密は 5 つある。秘密を入れるまでは、ログインが失敗する。

| 名前 | 値 |
| --- | --- |
| `DISCORD_CLIENT_ID` | 2.3 のクライアント ID |
| `DISCORD_CLIENT_SECRET` | 2.3 のクライアントシークレット |
| `DISCORD_GUILD_ID` | 2.3 のギルド ID |
| `DISCORD_ROLE_IDS` | 2.3 のロール ID。カンマ区切り |
| `SESSION_SECRET` | 暗号論的疑似乱数で生成した 32 バイトの値 |

`SESSION_SECRET` の値は、次のコマンドで作る。

```bash
openssl rand -base64 32
```

秘密は、名前ごとに次のコマンドで入れる。値は、コマンドが求めたときに入力する。引数には書かない。

```bash
npx wrangler secret put DISCORD_CLIENT_ID --env <環境名>
```

残りの 4 つも、名前を替えて同じコマンドで入れる。入れた名前は、次のコマンドで確かめられる。値は表示されない。

```bash
npx wrangler secret list --env <環境名>
```

### 5.4 Discord にリダイレクト URI を足す

Discord の開発者画面で、アプリケーションのリダイレクト URI に、次の URI を足す。

```
https://checkin-<環境名>.<アカウントのサブドメイン>.workers.dev/auth/discord/callback
```

受付アプリは、Worker が要求を受けたオリジンからこの URI を作る。登録した URI と 1 文字でも違うと、Discord が認可を拒む。

### 5.5 GitHub Actions からのデプロイを設定する

`main` への push で、GitHub Actions（リポジトリの直下の `.github/workflows/deploy.yml`）が、CI の通過後に 5.2 と同じ `deploy` を実行する（開発・環境構築手順書 8 章）。マイグレーションの適用（5.1）と秘密の設定（5.3）は行わない。使うには、次の 3 つを用意する。

1. デプロイ専用の API トークンを作る。管理者のトークン（2.2）は使い回さない。対象のアカウントをその環境のアカウントに限り、権限は Workers Scripts の Edit だけにする。リソースは、その環境の Worker（`checkin-<環境名>`）だけを指す Specific Workers に絞ってよい。D1 と Workers KV Storage の権限は付けない

   GitHub Actions の `deploy` は `--skip-remote-preflight` を付けて、D1 と KV を Cloudflare の API から直接読む事前検査（環境の印とマイグレーションの照合）を省く。D1 と KV の REST API は、Worker に絞ったトークンでは通らず、コード 7403（`The given account is not valid or is not authorized to access this service`）で止まったためである。この検査を省いても、未コミットの変更の検査と、設定ファイルの環境名の照合は行う。省いた分は、次の運用で補う
   - マイグレーションは、`main` へ入れる前に、管理者が手元で `migrate --env <環境名>` を実行しておく。CD は適用も照合もしない。未適用のまま Worker をデプロイすると、新しい Worker が古いスキーマを読む
   - 環境の取り違えは、`wrangler.jsonc` の `env` の `account_id`、D1 と KV の ID を変えるレビューと、環境の印を照合する管理者の手元の `deploy`（検査あり）で防ぐ。CD は、`deploy.yml` に書いた環境名の Worker にしか、デプロイしない

   管理者の手元の `deploy` は、`--skip-remote-preflight` を付けない。D1 と KV の Read を持つ管理者のトークン（2.2）で、検査を通す

   確かめていないこと: Specific Workers に絞った Workers Scripts の Edit だけで、既存の Worker のデプロイ（静的アセットのアップロードを含む）が通ること。Cloudflare の公式ドキュメントには、Specific Workers の権限範囲と、`wrangler deploy` が呼ぶ API の一覧は、見つからなかった。最初の実行で止まったら、止まった操作に要る権限を足し、この表を直す。新しい Worker を作るには、既存の Worker を指す Specific Workers では足りない可能性がある。新しい環境の最初のデプロイは、管理者の手元で行う

2. GitHub のリポジトリの Settings の Environments で、環境名と同じ名前の Environment を作る。Deployment branches and tags を Selected branches and tags にし、`main` だけを足す。このリポジトリは公開するので、`main` のほかのブランチの workflow からトークンを読めないようにするためである
3. その Environment の secret に、`CLOUDFLARE_API_TOKEN` の名前で、1 のトークンを入れる。リポジトリの secret には入れない

`deploy.yml` は、環境名を workflow の中に書いている。環境を足すときは、`deploy.yml` の環境名を書き換えるか、環境ごとのジョブを足す。

## 6. データを取り込んで公開する

イベントごとに、ZIP を取り込む。取り込みの出力は `.work/<環境名>/` に置かれ、参加者の情報を含む。

```bash
npm run admin -- import --env <環境名> --event <イベントの key> --zip <ZIP のパス>
```

取り込みが出すチケット種別とチケット番号の接頭辞が、指定したイベントのものであることを確かめる（PRD 9 章の 1）。ZIP のスラッグが `conference.slug` と違うと、取り込みは止まる（Design Doc 8.3）。

fortee がチケット番号を重ねて採番した参加者がいると、取り込みは、該当する CSV の行と補正ファイルのパスを出して止まる（Design Doc 8.3）。その行の `Ticket url` の末尾 32 文字（チケットトークン）を鍵に、fortee の参加者詳細画面の「QR」カードのプロフィールのリンク（`/attendee/{profile_url_token}/go-profile`）の 32 文字を値にして、補正ファイルに書く。重複した全員の分を書いてから、取り込み直す。

```json
{ "<チケットトークン>": "<profile_url_token>", "<チケットトークン>": "<profile_url_token>" }
```

補正ファイルは `.work/<環境名>/profile-url-tokens/<イベントの ID>.json` で、以後の取り込みでも読まれる。コミットしない。

参考情報テンプレートを使うときは、公開の前に、実在の参加者で描画を確かめる（Design Doc 8.7）。

```bash
npm run admin -- preview --env <環境名> --event <イベントの key> --ticket <チケット番号>
```

fortee がチケット番号を重ねて採番した参加者は、チケット番号では 1 人に決まらない。`--ticket` の代わりに、`--ticket-token <チケットトークン>`（CSV の `Ticket url` の末尾 32 文字）で指定する。

テンプレートには HTML を書ける（Design Doc 4.6）。改行と字下げは表示に出ないので、区切りは見出し、`<p>`、`<ul>`、`<br>` などのタグで書く。`preview` が出すのは、受付アプリが表示するのと同じ HTML の文字列で、参加者の値の中の `<` や `/` は文字参照（`&lt;`、`&#x2F;`）のまま出る。見え方は、公開の後に受付アプリの参考情報で確かめる。受付ごとに案内を出し分けるときは、`{{#reception.is.<受付の id>}}` か `{{#reception.checkin.<イベントの key>}}` で囲む（Design Doc 4.6）。このとき `preview` には `--reception <受付の id>` を付ける。付けないと受付なしの文脈になり、囲んだ部分は出ない。参加者の値（`{{…}}`）は、要素の中身か、引用符で囲んだ属性値にだけ置く。`href` などの URL の属性と、`<script>`、`<style>` の中には置かない。

すべてのイベントを取り込んだら、公開する。

```bash
npm run admin -- publish --env <環境名>
```

ここで公開するデータが本番の ZIP か、Sandbox や合成の ZIP かで、後の手順が変わる。本番の設定と本番の ZIP を公開し、本番のチケットの受付を始めた時点が運用の開始で、以後は記録を消せない。Sandbox や合成のデータを公開して確認に使った環境は、運用の開始の前に D1 と KV を作り直し、端末をログアウトする（開発・環境構築手順書 6 章、7 章）。試験のデータを本番環境に載せたくないときは、確認用の環境を別に作る（Design Doc 3.6）。

## 7. 構築を確かめる

次のことを確かめる。

| 確かめること | 方法 |
| --- | --- |
| デプロイしたリリース | 次のコマンドの出力に、5.2 のリリース名がある |
| ログイン | スマートフォンでオリジンを開き、受付スタッフのロールを持つ Discord のアカウントでログインできる。iOS では、ホーム画面に追加してから開く（NFR-8） |
| ロールの照合 | ロールを持たないアカウントでは、ログインが拒まれる |
| スナップショットの取得 | ログインの後、メニューのデータの版に、6 章で取り込んだ日時が出る |
| 管理者のロールとトークン | 3 章から 6 章のコマンドが、権限の不足で止まらずに通った（バックエンド 8.1） |

```bash
npx wrangler deployments list --env <環境名>
```

うまくいかないときは、止まったコマンドの出力を先に読む。管理 CLI が止まる主な場合は、次のとおりである。

| 出力 | 原因と対処 |
| --- | --- |
| `--env <環境名> を指定してください` | `--env` がない。既定値はない |
| `環境の印がありません` | `migrate` をまだ実行していない。5.1 を行う |
| `環境の印（…）が --env（…）と一致しません` | `wrangler.jsonc` の env に、別の環境の D1 か KV の ID を書いている。3.4 を見直す |
| `適用されていないマイグレーションがあります` | `migrate` をやり直す |
| `作業ツリーに未コミットの変更があります` | `fortee-reception/` 以下の変更をコミットしてから、`deploy` をやり直す。コミットする前の変更を実機で確かめるときだけ、`--dangerously-allow-dirty` を付ける。リリース名の末尾に、`-dirty-` と、変更の中身から求めた 7 文字が付く。中身を変えてデプロイし直すと、この 7 文字が変わる |

ログインが失敗するときは、秘密の名前（5.3 の `secret list`）と、リダイレクト URI（5.4）を見直す。Worker のログは、ダッシュボードの Workers Logs で読める（Design Doc 7.6）。
