# ドキュメント索引

fortee 連携チェックインシステムの文書である。fortee が発行するチケット QR を読み取り、カンファレンスごとに設定した受付ルールでチェックインを判定・記録し、結果を fortee に一括反映する仕組みを作る。

文書は 3 層に分かれる。docs 直下の PRD と画面設計書は要件と画面を定める文書、research/ は実装に先立って調べたことと選んだことの記録、Design Doc はその両方を前提にアプリケーションの設計を定める文書である。開発・環境構築手順書と本番環境構築手順書は、Design Doc の設計を前提に、開発、環境の構築、デプロイのコマンドの手順を定める。

実装するときは、どの部分でも PRD と Design Doc を先に読み、手元の開発の準備は開発・環境構築手順書に従う。受付アプリでは続けて画面設計書、research/ のフロントエンドと端末の挙動を、サーバと管理 CLI では research/ のバックエンドと fortee/ を読む。

## 文書のあいだの優先順位

- 要件は PRD が正である。画面設計書と PRD が食い違う場合は、画面の側で辻褄を合わせず PRD を直す
- 受付アプリの画面、要素、状態、文言は画面設計書が正である。カンプは参考にとどめ、食い違えば画面設計書に従う
- research/ のバックエンドとフロントエンドは、PRD と画面設計書を実現する手段を選んだ記録である。選んだ理由、比べた候補、実測の値、構築で確かめることはここにあり、選んだ結果の上で何をどう作るか（表と SQL、CSS の書き方、Service Worker の方式、テストの方針を含む）は Design Doc が定める。選定の文書と Design Doc が食い違う場合は Design Doc に従う。選定や設計の都合で要件や画面を変えるときは、PRD か画面設計書を直す
- 開発・環境構築手順書と本番環境構築手順書は、Design Doc の設計を実行するコマンドの手順である。手順書と Design Doc が食い違う場合は Design Doc に従い、手順書を直す
- research/fortee/ と端末の挙動は、こちらで変えられない fortee と端末の事実の記録である。fortee は調査日（2026-11-07）時点の仕様で、管理画面の API は公開仕様ではないので、利用前に Sandbox で再確認する

## 記述の確度

research/ のバックエンド、フロントエンド、端末の挙動は、冒頭に確度の表記（公式、実測、推定など）を定めている。fortee/ の表記は [research/fortee/README.md](research/fortee/README.md) にある。PRD、画面設計書、Design Doc は要件・画面・設計を定める文書であり、確度の表記は持たない。Design Doc の 12 章には、公式の文書と公開されたソースで確かめた事項の記録と、構築で確かめてから確定する事項（ローカルで確かめるものと、実機と実環境で確かめるもの）をまとめてある。
